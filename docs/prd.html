PRD v1.0 Scope Manager MVP 단계
제품 개요
Scope Manager PRD의 목적과 제품 목표, 전제 조건, 관련 문서 연결 구조를 정의합니다.
📌 이 문서의 목적과 사용 방법

이 PRD(Product Requirements Document)는 Scope Manager MVP를 만드는 데 필요한 모든 기능 요구사항, 우선순위, 포함/제외 범위, 완료 기준을 정의한다.

누가 이 문서를 사용하는가 — 현재 유일한 빌더인 Jey(PM 겸 기획자)가 Antigravity(AI IDE)에 프롬프트를 작성할 때 기준 문서로 활용한다. 기능 범위가 모호해질 때, 우선순위 결정이 필요할 때, 완료 여부를 확인할 때 이 문서로 돌아온다.

다른 기획 문서와의 관계 — 린캔버스(Why)와 사용자 리서치(Who)와 제품 비전(What & How)이 이미 완성되어 있다. 이 PRD는 그 위에서 구체적으로 무엇을 어떤 순서로 만드는가를 정의한다.

🎯 Product Goals — 제품 목표
💼 비즈니스 목표
  • 6주 내 Free → Paid 전환율 5% 이상 달성
  • 6개월 MRR 870,000원 (Starter 30개) — 손익분기점
  • 12개월 에이전시 누적 300개 이상 확보
  • 에이전시 커뮤니티 레퍼럴을 통한 자연 성장 채널 확보
  • PostHog 데이터로 PMF 신호 조기 포착
👤 사용자 목표
  • 클라이언트 요청 수신 후 30초 내 판정 결과 확인
  • PM이 직접 말하지 않고 리포트로 비용 청구 근거 전달
  • 프로젝트 진행 중 실시간 손익 파악 가능
  • 첫 리포트 생성 후 AHA 모멘트 경험 (Free → Paid 전환 트리거)
  • 범위 협상에서 개인 책임 부담 감소
🛠 기술 목표
  • Next.js 단일 스택으로 Python/FastAPI 없이 Claude API 연동
  • Supabase RLS로 멀티테넌트 데이터 완전 격리
  • Claude API Temperature 0.2 — 판정 일관성 확보
  • Fast Path 로직으로 API 호출 비용 최소화
  • Vercel 서버리스 배포로 인프라 관리 제로
⚠️ Assumptions & Constraints — 전제 조건 및 제약사항
✅ 전제 조건 (Assumptions)
  • 타겟 에이전시 PM은 기존 계약서·범위 정의 문서를 보유하고 있다
  • 클라이언트 추가 요청은 텍스트로 표현 가능한 형태로 들어온다
  • PM은 판정 결과를 직접 클라이언트에게 전달하는 역할을 유지한다
  • 초기 사용자는 데스크톱 브라우저로 접속한다
  • Supabase / Vercel / Claude API 서비스가 안정적으로 운영된다
  • MVP는 한국어 전용으로 시작한다 (다국어 불필요)
🚧 제약사항 (Constraints)
  • 기술 스택 고정 — Next.js 14 + Supabase + Claude API + Vercel (변경 불가)
  • 비개발자 빌더 — Antigravity AI IDE 의존, 복잡한 커스텀 인프라 불가
  • MVP 예산 제한 — Claude API 호출 비용 최소화 필수 (Fast Path 전략)
  • 데스크톱 우선 — 태블릿·모바일 반응형은 v1.1로 연기
  • 1인 개발 — 동시 다발적 기능 개발 불가, 순차 빌드 필수
  • 클라이언트 대면 기능 금지 — 내부 도구 원칙 (철회 불가)

영역 ① — Auth & Multi-tenant
인증 및 멀티테넌트 격리
P0 — MVP 필수
F-01 이메일 / 소셜 로그인
사용자 스토리
PM 또는 에이전시 대표로서, 이메일 또는 구글 계정으로 빠르게 가입·로그인하고 싶다. 그래야 추가 설정 없이 바로 프로젝트를 등록할 수 있다.
기술 노트
  • Supabase Auth 사용 — 이메일+패스워드 / Google OAuth
  • 가입 시 organizations 테이블에 워크스페이스 자동 생성
  • JWT 토큰 기반 세션 관리 (Supabase 기본 제공)
  • 이메일 인증 확인 후 온보딩 플로우 진입
세부 요구사항
  • 이메일 + 패스워드 회원가입 / 로그인 / 비밀번호 재설정 구현
  • Google OAuth 소셜 로그인 지원 (Supabase Auth Provider)
  • 가입 완료 시 워크스페이스(organization) 자동 생성 및 사용자-워크스페이스 연결
  • 미인증 상태에서 보호 경로 접근 시 /login 으로 리다이렉트
  • 로그인 상태 유지 (Remember me) — 기본 7일
F-02 워크스페이스 격리 & RLS 기반 데이터 보호 보안 필수
사용자 스토리
에이전시 대표로서, 우리 회사의 계약서·판정 기록·손익 데이터가 다른 에이전시에게 절대 노출되지 않아야 한다. 고객 정보 유출은 비즈니스 리스크다.
기술 노트
  • 모든 테이블에 organization_id 컬럼 필수
  • Supabase RLS Policy: SELECT/INSERT/UPDATE/DELETE 전체에 적용
  • Claude API 호출 시 프롬프트에 타 테넌트 데이터 미포함 검증 필수
  • 테넌트 간 프롬프트 오염 — 아키텍처 레벨에서 차단
세부 요구사항
  • 모든 DB 테이블에 RLS 활성화 — organization_id 기반 row 접근 제어
  • 사용자는 자신이 속한 organization의 데이터만 조회·수정·삭제 가능
  • API Route 레벨에서도 organization_id 검증 이중화
  • Claude API 프롬프트 구성 시 해당 organization 데이터만 컨텍스트로 주입
  • QA: 다른 organization 계정으로 데이터 접근 시도 → 403 반환 확인

영역 ② — Core Features
핵심 기능 — 범위 판정 · 리포트 생성
P0 — MVP 필수
F-03 프로젝트 생성 및 계약 범위 등록
사용자 스토리
PM으로서, 새 프로젝트를 만들고 계약서의 범위 내용을 텍스트로 입력해 등록하고 싶다. 그래야 클라이언트 요청이 왔을 때 AI가 이 기준으로 판정해줄 수 있다.
기술 노트
  • DB 테이블: projects, scope_definitions
  • 계약 범위 텍스트 → Claude API로 구조화 파싱 (1회 호출, 캐시)
  • 파싱 결과를 scope_definitions에 JSON으로 저장
  • 이후 판정 시 재파싱 없이 저장된 구조체 재사용 → API 비용 절감
세부 요구사항
  • 프로젝트명 / 클라이언트명 / 계약 시작일 / 계약 금액 입력 폼
  • 계약 범위 텍스트 자유 입력 (textarea, 최대 5,000자)
  • 범위 등록 완료 시 Claude API로 구조화 파싱 1회 실행 → 항목 리스트로 변환
  • 파싱된 항목 목록 PM이 확인·수정 가능한 미리보기 UI
  • 프로젝트 상태: 진행 중 / 완료 / 보류 3단계
  • 프로젝트 목록 페이지 — 최신순 정렬, 상태 필터
F-04 클라이언트 요청 입력 및 AI 범위 판정 AHA 모멘트 직전
사용자 스토리
PM으로서, 클라이언트의 추가 요청을 입력하면 AI가 30초 안에 계약 범위와 비교해서 "범위 내 / 초과 / 판단 필요" 중 하나로 판정해주길 원한다. 내가 직접 판단하지 않아도 된다.
기술 노트
  • Fast Path: 키워드 매칭으로 명확한 케이스 선처리 → Claude 호출 최소화
  • Claude API: temperature: 0.2 고정 — 일관성 확보
  • 프롬프트 구성: 계약 범위(구조체) + 클라이언트 요청 텍스트만 주입
  • 판정 결과 DB 저장: scope_requests 테이블
세부 요구사항
  • 클라이언트 요청 내용 텍스트 입력 (최대 2,000자)
  • 판정 결과 3단계: 범위 내 판단 필요 범위 초과
  • 판정 근거 표시 — 계약서 어느 항목과 비교했는지 근거 문장 함께 출력
  • 판정 소요 시간 목표: 30초 이내 (스트리밍 응답 고려)
  • 판정 결과 저장 — 히스토리 자동 누적
  • PM이 판정 결과에 동의 / 재판정 요청 가능 (수동 오버라이드)
F-05 판정 결과 리포트 자동 생성 AHA 모멘트
사용자 스토리
PM으로서, 범위 초과 판정 결과를 클라이언트에게 보낼 수 있는 공식 문서 형태로 자동 생성해주길 원한다. 내가 직접 문구를 쓰지 않고, 시스템 어조의 중립적 리포트를 받고 싶다.
기술 노트
  • 판정 후 리포트 생성은 별도 Claude API 호출 1회
  • 리포트 언어: 한국어, 중립적 시스템 어조, 계약 항목 번호 명시
  • 생성된 리포트 HTML/텍스트로 DB 저장
  • PDF 변환: Puppeteer 또는 브라우저 Print API 사용 검토
세부 요구사항
  • 리포트 구성: 프로젝트명 / 요청 일시 / 요청 내용 요약 / 판정 결과 / 계약 근거 / 추가 비용 안내 문구
  • PM이 리포트 내용 수정 후 확정 가능 (편집 모드)
  • 리포트 미리보기 — 클라이언트가 받게 될 형태로 렌더링
  • PDF 다운로드 버튼 (P0 MVP에서 구현)
  • 리포트 URL 공유 링크 생성 (선택 기능, P1 검토)
F-06 리포트 이메일 발송 / PDF 다운로드 P1 — Starter
사용자 스토리
PM으로서, 생성된 리포트를 클라이언트 이메일로 직접 발송하거나 PDF로 다운로드해서 첨부 파일로 보내고 싶다.
기술 노트
  • 이메일 발송: Resend 또는 Supabase Edge Functions 활용
  • 자동 발송 없음 — PM이 수동으로 발송 버튼 클릭 필수
  • 발송 이력 DB 기록 (발송 일시, 수신자)
  • PDF: 브라우저 window.print() 또는 서버사이드 생성 검토
세부 요구사항
  • 클라이언트 이메일 주소 입력 후 1클릭 발송
  • 발송 전 미리보기 확인 단계 필수 (실수 방지)
  • PDF 다운로드 — 리포트 확정 후 버튼 활성화
  • 발송 완료 후 리포트 상태 → "발송 완료"로 변경

P1 — Pro 업셀
F-07 프로젝트별 손익 누적 기록
사용자 스토리
에이전시 대표로서, 프로젝트가 끝나기 전에 추가 요청으로 인한 누적 손실을 실시간으로 파악하고 싶다. 다음 견적을 낼 때 이 데이터를 기준으로 단가를 조정할 수 있다.
기술 노트
  • 판정 결과에 추정 추가 비용 PM이 수동 입력
  • 청구 성공 / 미청구 상태 PM이 업데이트
  • 손익 계산: 계약금 - 추정 손실 누계
  • 집계는 DB 쿼리로 처리 — Claude API 불필요
세부 요구사항
  • 프로젝트별 추가 요청 건수 / 범위 초과 건수 / 청구 성공 건수 집계
  • 추정 손실액 누계 자동 계산 및 표시
  • 손익 상태 시각화: 흑자 주의 적자 3단계 배지
  • 프로젝트 완료 시 최종 손익 리포트 요약 생성
F-08 추가 요청 히스토리 타임라인
사용자 스토리
PM으로서, 프로젝트 전체 기간 동안 들어온 모든 추가 요청의 판정 이력을 시간 순으로 확인하고 싶다. 클라이언트와 분쟁이 생겼을 때 이 기록이 근거가 된다.
기술 노트
  • scope_requests 테이블 created_at 기준 정렬
  • 타임라인 UI — 날짜별 그룹핑, 판정 결과 색상 구분
  • 페이지네이션 또는 가상 스크롤 (데이터 다량 대비)
  • Claude API 추가 호출 불필요 — DB 조회만으로 구현
세부 요구사항
  • 요청 일시 / 요청 내용 요약 / 판정 결과 / 리포트 발송 여부 / 청구 상태 표시
  • 판정 결과별 필터 (전체 / 범위 내 / 범위 초과 / 판단 필요)
  • 개별 요청 클릭 시 상세 판정 결과 및 리포트 확인
  • CSV 내보내기 (P2 기능, 지금은 UI 준비만)
F-09 핵심 지표 요약 뷰 (홈 대시보드)
사용자 스토리
에이전시 대표로서, 로그인하면 전체 프로젝트의 현황을 한 화면에서 파악하고 싶다. 어떤 프로젝트가 위험한지, 이번 달 추가 요청이 얼마나 됐는지 즉시 보여야 한다.
기술 노트
  • 집계 쿼리 Supabase 뷰(View)로 최적화
  • PostHog 이벤트 연동 — 대시보드 방문 / 지표 클릭 트래킹
  • 실시간 업데이트: Supabase Realtime 또는 주기 폴링 검토
  • Claude API 불필요 — 순수 집계 데이터
세부 요구사항
  • 진행 중 프로젝트 수 / 이번 달 추가 요청 건수 / 청구 성공 건수 / 누적 방어 금액 4개 핵심 수치 카드
  • 손익 위험 프로젝트 목록 — 적자 가능성 높은 순 정렬
  • 최근 판정 이력 5건 빠른 확인
  • 로그인 직후 랜딩 화면으로 사용 (홈 대시보드)

⚡ Fast Path 로직 — Claude API 호출 최소화 전략
💡 왜 Fast Path가 필요한가

Claude API는 호출당 비용이 발생한다. MVP 단계에서는 수익이 없는 상태에서 무제한 API 호출이 발생하면 운영 적자로 이어진다. 판정 요청의 상당수는 AI 없이도 규칙 기반으로 처리 가능하다 — 이 케이스를 먼저 걸러내면 API 비용을 대폭 절감할 수 있다.

✅ Fast Path — Claude API 호출 안 하는 경우
  • 완전 일치 — 요청 키워드가 계약 범위 항목과 100% 일치 → 범위 내 즉시 반환
  • 명백한 신규 항목 — 요청 내용이 등록된 범위 카테고리 어디에도 없는 키워드 → 범위 초과 즉시 반환
  • 중복 요청 — 동일 프로젝트에서 이전에 판정된 동일 요청 → 캐시된 결과 재사용
  • PM 수동 오버라이드 — PM이 이전에 직접 판정한 유형과 동일 패턴 → 오버라이드 기록 우선 적용
🤖 Claude API 호출하는 경우
  • 애매한 요청 — 범위 항목과 부분적으로 겹치거나 해석이 필요한 경우
  • 복합 요청 — 여러 기능이 혼합된 요청 (일부 범위 내 + 일부 초과)
  • 신규 카테고리 — 기존 판정 이력이 없는 처음 보는 요청 유형
  • 계약 범위 최초 파싱 — 프로젝트 생성 시 계약 텍스트 구조화 (1회만)
  • 리포트 생성 — 범위 초과 판정 후 문서화 (1회만)

🔲 범위 정의가 중요한 이유

무엇을 만들지 못지않게 무엇을 만들지 않는지를 명확히 해야 한다. 범위가 불명확하면 빌드 세션마다 "이것도 해야 하나?"라는 결정을 반복하게 되고, 결국 MVP가 늦어진다. 이 탭의 목록은 Antigravity 빌드 프롬프트 작성 시 포함 여부 확인 체크리스트로 사용한다.

🔒 데이터 범위 — 멀티테넌트 격리 아키텍처
📐 DB 스키마 설계 원칙
  • 모든 테이블: organization_id UUID NOT NULL 필수
  • 모든 테이블: Supabase RLS ENABLE FORCE 적용
  • RLS Policy: auth.uid() → organization_members → organization_id 체인 검증
  • 핵심 테이블: organizations / projects / scope_definitions / scope_requests / reports
  • 외래키 cascade 설정 — organization 삭제 시 하위 데이터 전체 삭제
⚠️ 테넌트 간 프롬프트 오염 방지
  • Claude API 프롬프트 구성 시 해당 organization_id 데이터만 쿼리
  • API Route 레벨에서 organization_id 파라미터 검증 이중화
  • Supabase 쿼리에 RLS 의존만 하지 않고 WHERE organization_id = ? 명시 추가
  • QA 시나리오: 타 organization 토큰으로 데이터 접근 → 403 반환 필수
  • 프롬프트 로깅 비활성화 — 계약서 내용 외부 노출 차단

✅ 인수 기준(Acceptance Criteria)이란

각 기능이 "완료됐다"고 판단할 수 있는 최소 기준이다. 이 기준을 통과하지 못한 기능은 배포하지 않는다. Antigravity 빌드 세션 후 직접 이 체크리스트를 확인해 검증한다.

☐ 기능별 완료 기준 (Definition of Done)
🔐 F-01 · F-02 — 인증 & 멀티테넌트
  • 이메일 가입 → 이메일 인증 메일 수신 → 인증 후 로그인 성공
  • Google OAuth 로그인 → 계정 선택 → 대시보드 랜딩 성공
  • 가입 완료 시 organizations 테이블에 레코드 자동 생성 확인
  • 비밀번호 재설정 이메일 수신 → 재설정 성공
  • 미인증 URL 직접 접근 → /login 리다이렉트 확인
  • 모든 DB 테이블 RLS ENABLED 상태 Supabase 대시보드에서 확인
  • 계정 A로 생성한 프로젝트를 계정 B로 조회 → 빈 결과 반환 확인
  • 계정 B 토큰으로 계정 A 프로젝트 ID 직접 API 요청 → 403 반환 확인
  • Claude API 프롬프트에 타 organization 데이터 미포함 코드 리뷰 완료
⚙️ F-03 · F-04 · F-05 — 핵심 기능
  • 프로젝트 생성 폼 제출 → projects 테이블 레코드 생성 확인
  • 계약 범위 텍스트 등록 → Claude API 1회 호출 → 구조화 결과 미리보기 표시
  • Fast Path: 동일 요청 재입력 → Claude API 재호출 없이 캐시 결과 반환 확인
  • 판정 결과 3단계 색상 정상 표시 — 범위 내 판단 필요 범위 초과
  • 판정 근거 문장 — 계약서 항목과 연결된 근거 텍스트 출력 확인
  • 범위 초과 판정 후 리포트 생성 버튼 클릭 → 리포트 초안 표시
  • 리포트 내용 PM이 수정 → 저장 → 수정 내용 반영 확인
  • 리포트 확정 후 PDF 다운로드 정상 작동
  • 생성된 리포트 중립적 시스템 어조 확인 (감정적 언어 없음)
  • 판정 이력 scope_requests 테이블에 자동 저장 확인
📊 PostHog 분석 연동
  • 회원 가입 완료 이벤트 user_signed_up PostHog에서 수신 확인
  • 첫 판정 완료 이벤트 first_scope_judgment 수신 확인
  • 리포트 생성 이벤트 report_generated 수신 확인 — AHA 모멘트 추적
  • PDF 다운로드 이벤트 수신 확인
  • 이탈 시점 세션 데이터 수집 확인
  • 사용자 식별자(organization_id) 연결 — 익명 데이터 최소화
🚀 MVP 배포 전 필수 통과 기준 — Go / No-Go 체크리스트
기능 완료 조건 (Go 조건)
  • F-01 ~ F-05 모든 DoD 체크리스트 100% 통과
  • 가입 → 계약 등록 → 판정 → 리포트 생성 엔드투엔드 플로우 성공
  • RLS 격리 QA 시나리오 전체 통과 (403 반환 포함)
  • PostHog 핵심 이벤트 5개 이상 수신 확인
  • Vercel 프로덕션 환경에서 정상 작동 확인
배포 차단 조건 (No-Go 조건)
  • 타 테넌트 데이터 접근 가능한 버그 존재
  • Claude API 키가 클라이언트 코드에 노출된 상태
  • 판정 결과가 저장되지 않는 DB 버그
  • PDF 다운로드 기능 미작동
  • PostHog 트래킹 이벤트 미수신
  • 로그인 없이 보호 경로 접근 가능한 버그
