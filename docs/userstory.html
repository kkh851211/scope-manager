📌 이 문서의 목적과 사용 방법

이 문서는 Scope Manager MVP를 사용하는 실제 사람들의 관점에서 기능을 재정의한다. PRD가 "무엇을 만드는가(What)"를 정의했다면, 이 문서는 "누가, 왜, 어떤 순서로 쓰는가(Who · Why · How)"를 정의한다.

누가 이 문서를 사용하는가 — Antigravity(AI IDE)에 UI·UX 프롬프트를 작성할 때, 화면 흐름과 인터랙션 설계의 기준 문서로 활용한다. 기능 개발 후 "이 화면에서 유저가 다음에 뭘 해야 하지?"가 불분명할 때 이 문서로 돌아온다.

PRD와의 관계 — PRD의 F-01~F-09 기능 요구사항이 이 문서의 유저 스토리 근거가 된다. 유저 스토리는 PRD 기능을 사용자 언어로 번역한 것이고, 유저 플로우는 그 스토리들을 시간 순서로 연결한 것이다.

📖 유저 스토리(User Story)란 무엇인가
정의
유저 스토리는 사용자의 목표와 동기를 한 문장으로 압축한 요구사항 표현 방식이다. 기능 명세서(PRD)가 시스템 관점에서 "무엇을 만드는가"를 쓴다면, 유저 스토리는 사용자 관점에서 "나는 왜 이걸 원하는가"를 쓴다.
이 문서의 작성 형식
OO로서,
OO를 하기 위해,
OO를 한다.
OO로서 — 역할(페르소나)
OO를 하기 위해 — 목적(Why)
OO를 한다 — 행동(What)
작성 예시
✅ 좋은 유저 스토리
에이전시 대표로서,
클라이언트와의 분쟁 시 근거를 제시하기 위해,
모든 판정 이력이 자동 저장되는 히스토리 타임라인을 확인한다.
✕ 나쁜 유저 스토리 (기능 명세식)
"히스토리 타임라인 페이지를 만든다.
scope_requests 테이블을 created_at 기준으로 정렬해서 표시한다."
→ 사용자 목적(Why)이 빠진 기술 명세. PRD에 적합, 유저 스토리에 부적합.
📐 유저 스토리 작성 원칙
🎯
목적 중심으로 쓴다
"버튼을 클릭한다"가 아니라 "왜 그 버튼을 클릭하는가"에 초점을 둔다. 구현 방식이 아닌 사용자의 목표와 동기를 담는다.
👤
역할을 구체적으로 쓴다
"사용자로서"가 아닌 "에이전시 대표로서" / "전담 PM으로서"처럼 구체적 역할로 명시한다. 역할이 다르면 같은 기능도 다른 이유로 쓴다.
✂️
하나의 스토리 = 하나의 목표
한 문장에 여러 목표를 담지 않는다. 독립적으로 테스트·검증 가능한 단위로 쪼갠다. 크다 싶으면 더 작게 나눈다.

🔗 PRD와의 관계 — 이 문서가 연결되는 위치
⚠️ 유저 스토리 ≠ PRD 기능 요구사항

PRD의 기능 요구사항(F-01~F-09)은 "시스템이 무엇을 해야 하는가"를 정의한다. 이 문서의 유저 스토리는 "사람이 왜 그 기능을 원하는가"를 정의한다. 두 문서는 서로를 설명하는 관계이지, 하나가 다른 하나를 대체하지 않는다.

Antigravity에서 UI 화면을 만들 때 PRD(기능 스펙) + 유저 스토리/플로우(맥락·동기·흐름)를 함께 참고할 때 가장 정확한 결과물이 나온다.

에이전시 대표 — 유저 스토리
수익성 파악, 손익 관리, 전략적 의사결정 관점에서 에이전시 대표가 Scope Manager를 사용하는 이유와 행동을 정의합니다.
🏢
에이전시 대표 · PM 겸직 · 결제 권한자
직원 5~20인 규모의 웹 에이전시를 운영하며 PM 업무를 직접 수행한다. 클라이언트 관계를 유지하면서도 수익성을 지켜야 하는 이중의 압박 속에 있다. 프로젝트가 끝난 후에야 손실을 알게 되는 구조를 바꾸고 싶다. Scope Manager는 그에게 "시스템이 판정했다"는 프레임을 제공해 개인 관계를 지키면서 수익을 방어하게 한다.

US-O-01 F-01 P0 Auth
에이전시 대표로서,
바쁜 업무 중에도 빠르게 도구에 접속하기 위해,
구글 계정으로 1클릭 로그인해 별도 가입 절차 없이 바로 대시보드에 진입한다.
배경 — 대표는 미팅·견적·현장 대응으로 시간이 없다. 가입 폼을 채우는 마찰이 크면 첫 사용을 포기한다. Google OAuth로 진입 장벽을 최소화해야 한다.
US-O-02 F-02 P0 보안
에이전시 대표로서,
경쟁사나 타 에이전시에 우리 회사의 계약 정보와 클라이언트 데이터가 절대 유출되지 않도록 하기 위해,
우리 워크스페이스의 데이터가 다른 에이전시와 완전히 분리된 독립 공간에 저장된다는 것을 확인한다.
배경 — 계약서와 손익 데이터는 핵심 영업 자산이다. 멀티테넌트 환경에서 데이터 격리가 보장되지 않으면 SaaS 도구를 도입할 수 없다.

배경 — 대표는 여러 프로젝트를 동시에 신경 써야 한다. 각 프로젝트를 하나씩 열어보는 게 아니라 한 화면에서 "어디에 집중해야 하는가"를 파악해야 한다.

P0

배경 — 전담 PM은 여러 클라이언트 프로젝트를 관리하며 각 계약 정보가 외부에 노출되지 않아야 한다. 로그인 후 바로 내 프로젝트 목록이 보여야 업무 흐름이 끊기지 않는다.

PM으로서,
클라이언트 추가 요청이 왔을 때 즉시 판정 기준을 확인하기 위해,

배경 — 프로젝트 생성과 계약 범위 등록은 AI 판정의 전제 조건이다. 이 단계가 빠르고 쉬울수록 실제 사용까지의 진입 장벽이 낮아진다. 계약서를 그대로 붙여넣을 수 있어야 한다.

범위 텍스트 등록 직후 AI가 파싱한 항목 목록을 미리보기로 검토하고 필요 시 수정한다.
배경 — 계약서를 붙여넣으면 AI가 구조화한 결과를 즉시 확인할 수 있어야 "이게 맞게 들어갔나?" 불안 없이 사용을 시작할 수 있다.

판정 결과의 근거를 이해하고 클라이언트에게 설명할 수 있도록 하기 위해,
판정 결과와 함께 계약서의 어느 항목과 비교해 이 결론이 나왔는지 근거 문장을 함께 확인한다.
배경 — "AI가 초과라고 했어요"만으로는 설득력이 약하다. "계약서 3항에 명시된 OO 범위와 비교 시 초과입니다"처럼 근거가 있어야 클라이언트 설명이 가능하다.
US-P-06 F-04 P0 전담 PM
전담 PM으로서,
AI 판정이 명백히 틀렸다고 판단될 때 올바른 결과를 기록으로 남기기 위해,
판정 결과에 동의하지 않을 경우 수동 오버라이드로 직접 결과를 수정하고 저장한다.
배경 — AI 판정이 항상 완벽하지 않다. PM이 맥락을 더 잘 알 수 있고, 그 경우 수동 보정이 가능해야 신뢰도를 유지할 수 있다. 오버라이드 기록은 이후 Fast Path 학습에도 활용된다.

리포트 생성 & 전달 AHA 모멘트
P0~P1
US-P-07 F-05 P0 PM 겸직 전담 PM ⭐ AHA
PM으로서,
추가 비용 청구 이유를 클라이언트에게 감정 없이 전달하기 위해,
범위 초과 판정 직후 중립적 시스템 어조의 청구 근거 리포트를 자동으로 생성한다.
배경 — 이것이 AHA 모멘트다. PM이 직접 쓴 문서가 아닌, 시스템이 생성한 공식 문서라는 프레임이 클라이언트 설득력을 높이고 PM의 심리적 부담을 낮춘다.
US-P-08 F-05 P0 PM 겸직
PM 겸직 시니어로서,
리포트를 클라이언트에게 보내기 전에 어조와 내용이 적절한지 검토하기 위해,
자동 생성된 리포트 초안을 편집 모드에서 수정한 뒤 최종 확정한다.
배경 — 클라이언트마다 소통 방식이 다르다. 어떤 클라이언트는 직접적인 표현이, 어떤 클라이언트는 부드러운 표현이 더 효과적이다. PM이 최종 조율권을 가져야 한다.
US-P-09 F-05 P0 전담 PM
전담 PM으로서,
리포트를 클라이언트에게 이메일이나 메신저로 즉시 공유하기 위해,
확정된 리포트를 PDF로 다운로드해 첨부 파일로 전달한다.
배경 — PDF는 수정이 어렵고 날짜·로고가 찍힌 공식 문서 형태라 클라이언트가 "정식 통보"로 받아들인다. 이메일 본문보다 PDF 첨부가 더 공식적이다.
US-P-10 F-06 P1 PM 겸직 전담 PM
PM으로서,
리포트 전달 후 발송 이력을 체계적으로 관리하기 위해,
리포트 이메일 발송 후 "발송 완료" 상태로 자동 변경되고 발송 이력이 기록되는 것을 확인한다.
배경 — "언제, 누구에게 보냈는가"의 기록이 있으면 나중에 "못 받았다"는 클라이언트 주장을 반박할 수 있다. 발송 이력 자체가 증빙이 된다.

STEP 1 — 가입 & 로그인
🔑
가입 & 로그인
연결 기능: F-01 F-02 · 목표 소요 시간: 1분 이내
P0
👤 유저 액션
  • 랜딩 페이지에서 "무료로 시작하기" 버튼 클릭
  • Google 계정으로 소셜 로그인 또는 이메일 + 비밀번호 입력
  • 이메일 가입 시 인증 메일 확인 후 링크 클릭
  • 로그인 완료 → 대시보드 또는 온보딩 화면 진입
⚙️ 시스템 반응
  • Supabase Auth로 JWT 세션 토큰 발급
  • organizations 테이블에 워크스페이스 자동 생성
  • organization_members에 사용자-워크스페이스 연결 레코드 생성
  • PostHog user_signed_up 이벤트 전송
  • 첫 로그인 감지 시 온보딩 가이드 화면으로 리다이렉트
⚠️ 이탈 위험 포인트
이메일 인증 대기 이탈 — 인증 메일이 스팸함에 들어가거나 느리게 도착하면 이탈. → Google OAuth 우선 노출로 마찰 최소화.
가입 후 "이제 뭘 해야 하지?" 혼란 — 빈 대시보드에 착지하면 다음 액션이 불명확. → 첫 로그인 시 온보딩 가이드 자동 표시 필수.
STEP 2 — 워크스페이스 자동 생성 확인
🏢
워크스페이스 자동 생성 확인
연결 기능: F-02 · 목표 소요 시간: 자동 처리 (0초)
P0
👤 유저 액션
  • 가입 직후 온보딩 화면에서 에이전시(회사) 이름 입력
  • "시작하기" 버튼 클릭으로 워크스페이스 설정 완료
  • 별도의 복잡한 설정 없이 바로 다음 단계(프로젝트 등록)로 이동
⚙️ 시스템 반응
  • 입력한 에이전시명으로 organizations.name 업데이트
  • 헤더에 워크스페이스 이름 즉시 표시 → "내 공간" 인식 강화
  • 모든 이후 DB 레코드에 organization_id 자동 연결
  • 온보딩 진행률 표시 (1/4 완료)
⚠️ 이탈 위험 포인트
설정 단계가 너무 많으면 이탈 — 워크스페이스 설정은 최소한(이름 1개 입력)으로 끝내야 한다. 추가 프로필 입력은 나중으로 미룬다.
STEP 3 — 첫 프로젝트 등록
📁
첫 프로젝트 등록
연결 기능: F-03 · 목표 소요 시간: 2분 이내
P0
👤 유저 액션
  • "첫 프로젝트 만들기" CTA 버튼 클릭
  • 프로젝트명 / 클라이언트명 / 계약 시작일 / 계약 금액 입력
  • 프로젝트 상태 선택 (기본값: 진행 중)
  • "다음 단계 — 계약 범위 입력" 버튼 클릭
⚙️ 시스템 반응
  • projects 테이블에 레코드 생성 (organization_id 자동 연결)
  • 저장 즉시 계약 범위 입력 단계로 자동 전환
  • 온보딩 진행률 표시 (2/4 완료)
  • 브레드크럼(breadcrumb)에 프로젝트명 즉시 표시
⚠️ 이탈 위험 포인트
"지금 당장 등록할 프로젝트가 없어요" — 실제 진행 중인 프로젝트가 없거나, 계약서가 손에 없는 경우. → 샘플 프로젝트(데모 데이터)로 먼저 체험할 수 있는 옵션 제공.
필수 입력 항목이 많으면 이탈 — 프로젝트명과 클라이언트명만 최소 필수, 나머지는 선택 입력으로 처리해야 한다.
STEP 4 — 계약 범위 입력 & AI 파싱
📝
계약 범위 입력 & AI 파싱
연결 기능: F-03 · Claude API 1회 호출 · 목표 소요 시간: 3분 이내
P0
👤 유저 액션
  • 계약서 또는 범위 정의 문서에서 텍스트를 복사해 붙여넣기
  • 또는 직접 범위 내용을 자유 형식으로 타이핑
  • "AI 범위 파싱 시작" 버튼 클릭
  • 파싱된 항목 목록 검토 → 필요 시 수정 또는 항목 추가/삭제
  • "파싱 결과 확정" 버튼 클릭 → 다음 단계로 이동
⚙️ 시스템 반응
  • 파싱 버튼 클릭 시 로딩 인디케이터 + "AI가 계약 범위를 분석 중입니다" 안내
  • Claude API 호출 (temperature 0.2) → 항목 리스트로 구조화
  • scope_definitions 테이블에 JSON으로 저장
  • 파싱 결과를 편집 가능한 항목 카드 형태로 렌더링
  • 확정 클릭 시 온보딩 진행률 (3/4 완료)
💡 범위 입력 예시 — UI에서 힌트로 제공
"본 계약의 개발 범위는 다음과 같습니다: ① 메인 홈페이지 반응형 퍼블리싱 (PC/모바일), ② 회사 소개, 서비스 소개, 포트폴리오, 문의 총 5개 페이지, ③ 관리자 페이지 기본 기능 (게시글 CRUD), ④ 1회 디자인 시안 제공 및 2회 수정 포함. 범위 외 추가 페이지, 기능 개발, 3회 이상 디자인 수정은 별도 견적으로 처리합니다."
⚠️ 이탈 위험 포인트
AI 파싱 결과가 기대 이하 — 구조화 결과가 엉터리면 신뢰를 잃고 이탈. → 파싱 후 PM이 항목을 직접 수정할 수 있는 편집 모드가 필수.
"계약서가 지금 없어요" — 계약서를 가지러 이탈 후 미복귀. → 임시 저장 기능 + "나중에 범위 입력" 스킵 옵션(단, 판정 불가 안내 포함) 제공.
STEP 5 — 첫 클라이언트 요청 입력 & AI 판정
🤖
첫 클라이언트 요청 입력 & AI 판정
연결 기능: F-04 · Claude API 호출 (Fast Path 미적중 시) · 목표: 30초 이내 결과
P0
👤 유저 액션
  • 클라이언트에게 받은 추가 요청 내용을 텍스트로 붙여넣기 또는 직접 입력
  • "범위 판정 요청" 버튼 클릭
  • 판정 결과(범위 내 / 판단 필요 / 범위 초과) 및 근거 문장 확인
  • 결과에 동의하면 "확인" 클릭, 이의 있으면 "재판정 요청" 클릭
⚙️ 시스템 반응
  • Fast Path 체크 → 캐시 미적중 시 Claude API 호출
  • 스트리밍 응답으로 판정 결과 실시간 렌더링
  • 판정 결과 3단계 색상 배지로 시각화 표시
  • 근거 문장 — 계약서 항목 번호와 연결해서 출력
  • scope_requests 테이블에 자동 저장
  • PostHog first_scope_judgment 이벤트 전송
⚠️ 이탈 위험 포인트
판정이 30초를 넘을 경우 — 무반응 로딩은 불안감을 준다. → 스트리밍 응답 + 단계별 진행 메시지("계약 범위 분석 중 → 요청 비교 중 → 판정 완료") 표시.
판정 결과가 납득 안 될 경우 — 틀린 판정에 신뢰를 잃으면 재사용 안 함. → 수동 오버라이드 옵션 항상 노출. "이 판정이 잘못됐나요?" 피드백 버튼 제공.

📌 이 플로우가 다루는 시나리오

클라이언트로부터 계약 외 추가 요청이 들어왔을 때 PM이 수행하는 표준 대응 플로우다. 가장 빈번하게 반복되는 핵심 업무 흐름이며, 이 플로우가 매끄러울수록 제품의 Daily Active Use가 높아진다.

전체 흐름 — 4단계
1
📨 클라이언트 요청 수신 & 입력
👤 유저 액션
  • 이메일·메신저로 받은 클라이언트 요청 내용을 복사
  • 해당 프로젝트 선택 후 "추가 요청 판정" 입력창에 붙여넣기
  • 필요 시 맥락 설명 추가 후 "범위 판정 요청" 클릭
⚙️ 시스템 반응
  • 입력 텍스트 유효성 검사 (최대 2,000자)
  • 해당 프로젝트의 scope_definitions 로드
  • Fast Path 체크 선행 실행 → 분기 결정
💡 유저 스토리 연결 — US-P-04: PM으로서, 객관적 근거를 얻기 위해, 요청 내용을 입력하고 AI 판정 결과를 받는다.

  • 판정 결과 수신 후 결과 배지와 근거 문장 검토
  • 결과에 동의하면 "확인" 클릭, 이견 있으면 "재판정"
⚙️ 시스템 반응
  • Claude API 호출 (temperature 0.2) · 스트리밍 응답
  • 판정 결과 3단계 색상 배지 렌더링
  • 근거 문장 + 연결 계약 항목 번호 출력
  • scope_requests 테이블 저장 · PostHog 이벤트

  • 어조·금액·추가 문구 필요 시 편집 모드에서 수정

  • 다운로드된 PDF 파일을 이메일·메신저에 첨부해 전달

  • 브라우저 Print API / Puppeteer로 PDF 변환 후 다운로드
  • 리포트 상태 → "PDF 생성 완료"로 업데이트
  • (P1) 이메일 발송 시 상태 → "발송 완료", 발송 이력 기록
  • PostHog pdf_downloaded 이벤트
💡 유저 스토리 연결 — US-P-09: 전담 PM으로서, 클라이언트에게 즉시 공유하기 위해, 확정된 리포트를 PDF로 다운로드해 첨부 파일로 전달한다.
⚡ 플로우 ② — Fast Path 분기 플로우 (Claude API 호출 최소화)
💡 Fast Path가 존재하는 이유

모든 판정 요청을 Claude API로 처리하면 호출 비용이 선형으로 증가한다. 전체 요청의 30~40%는 규칙 기반으로 즉시 처리 가능하다. Fast Path는 이 케이스를 먼저 걸러내 응답 속도를 높이고 API 비용을 절감하는 전략이다.

요청 키워드가 scope_definitions의 항목과 정확히 매칭될 때. 예: "반응형 홈페이지"가 계약 범위에 "반응형 퍼블리싱"으로 등록된 경우.

결과: 범위 초과 즉시 반환 · Claude API 호출 없음 · 응답 <1초

결과: 캐시된 판정 결과 즉시 반환 · Claude API 호출 없음 · 응답 <1초
🤖 경로 D — Claude API 호출 (Fast Path 미적중)

결과: Claude API 호출 · 스트리밍 응답 · 판정 결과 캐시 저장 (재호출 방지)

🔄 플로우 ③ — PM 수동 오버라이드 플로우
🔄 PM 오버라이드가 필요한 이유

AI 판정이 항상 완벽하지 않다. 계약서에 명시되지 않은 구두 합의나 프로젝트 고유 맥락은 AI가 알 수 없다. PM이 더 정확한 판단을 내릴 수 있을 때 오버라이드 권한이 있어야 시스템에 대한 신뢰가 유지된다. 오버라이드 기록은 이후 Fast Path 경로 C의 캐시 데이터로도 활용된다.

PM 오버라이드 플로우 — 3가지 진입 경로
1
🤖 AI 판정 결과 수신 — 오버라이드 트리거 발생
AI 판정 결과를 확인한 PM이 결과가 맥락에 맞지 않는다고 판단할 때 오버라이드를 시작한다.
시나리오 A
"범위 초과"로 나왔는데 사실 구두로 포함하기로 했음 → 범위 내로 변경
시나리오 B
"판단 필요"로 나왔는데 PM이 확실히 초과라고 판단 → 범위 초과로 변경
시나리오 C
"범위 내"로 나왔는데 계약서 재확인 시 명백한 초과 → 범위 초과로 변경
2
✏️ 수동 오버라이드 실행
👤 유저 액션
  • 판정 결과 화면 하단의 "이 판정에 이의 있음" 버튼 클릭
  • 오버라이드 모달에서 변경할 결과 선택 (범위 내 / 판단 필요 / 범위 초과)
  • 오버라이드 사유 텍스트 입력 (선택, 권장)
  • "오버라이드 저장" 클릭
⚙️ 시스템 반응
  • scope_requests의 판정 결과 업데이트
  • 원래 AI 판정 결과는 보존 (감사 로그)
  • 오버라이드 사유 별도 컬럼에 저장
  • 해당 패턴을 Fast Path 캐시에 등록 → 동일 유형 재요청 시 재활용
  • 판정 결과 배지 업데이트 + PM 수정 표시
💡 유저 스토리 연결 — US-P-06: 전담 PM으로서, AI 판정이 틀렸다고 판단될 때 올바른 결과를 기록으로 남기기 위해, 수동 오버라이드로 직접 결과를 수정하고 저장한다.
3
✅ 오버라이드 이후 — 후속 처리 분기
범위 초과로 오버라이드 시
  • "리포트 자동 생성" 버튼 활성화
  • 플로우 ①의 STEP 3~4 그대로 이어서 진행
  • 리포트에 "PM 검토 후 판정" 문구 자동 추가
범위 내로 오버라이드 시
  • 리포트 생성 불필요 — 히스토리에만 기록
  • 오버라이드 사유가 내부 메모로 저장
  • 동일 유형 재요청 시 Fast Path 경로 C로 처리
🔁 Fast Path 학습 효과
PM의 오버라이드 기록이 누적될수록 Fast Path 캐시가 풍부해진다. 같은 에이전시·같은 유형의 요청은 점차 Claude API 없이 빠르게 처리된다 — API 비용이 사용할수록 줄어드는 구조.
