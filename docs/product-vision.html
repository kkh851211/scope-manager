🌱 Why We Exist — 우리가 존재하는 이유
현실에서 출발한 문제
한국 웹 에이전시 PM은 매 프로젝트마다 같은 선택 앞에 선다.

클라이언트가 계약에 없는 요구를 한다. PM은 "추가 비용이 발생합니다"라고 말해야 한다는 것을 안다. 하지만 말을 꺼내지 못한다.
  • 관계가 손상될까봐 — 청구를 포기한다
  • 기준이 없으니까 — 담력 싸움이 된다
  • 혼자 감당해야 하니까 — 조용히 손해를 본다
사용자 리서치 결과: 추가 요구 비용 청구 포기율 68%
인터뷰 3인 모두 "그냥 해준다"가 기본값임을 확인
우리가 발견한 해결의 실마리
인터뷰에서 한 PM이 말했다.

"만약 '시스템이 범위 초과라고 판정했다'고 클라이언트한테 보여줄 수 있으면… 그게 저를 지켜주는 거잖아요."
문제는 용기의 부재가 아니다. 구조의 부재다.

PM이 말하면 감정 싸움이 된다.
시스템이 판정하면 데이터 대화가 된다.

Scope Manager는 그 구조를 만든다.

💭 What We Believe — 우리가 믿는 것들
①
"용기 부족"이 아니라 "구조 부족"이다
PM이 추가 비용을 청구하지 못하는 이유는 소심해서가 아니다. 감정 싸움을 데이터 대화로 바꿔줄 구조가 없어서다. 우리는 그 구조를 만드는 것이 제품의 역할이라고 믿는다.
②
관계와 수익은 트레이드오프가 아니다
범위를 지키는 일이 관계를 해치는 일일 필요가 없다. "제가 그러는 게 아니라 시스템이 판정했습니다"는 한 문장이 PM을 갈등의 당사자에서 중립적 전달자로 바꾼다.
③
행동 데이터가 설문보다 정직하다
고객 인터뷰보다 실제 사용·이탈 패턴이 더 정직한 검증 신호다. 우리는 MVP를 먼저 배포하고 행동으로 가설을 검증한다. AI가 개발 비용을 낮춘 덕분에 이 순서가 가능해졌다.
④
정직한 포지셔닝이 장기 신뢰를 만든다
우리는 Scope Manager가 완전히 해결하는 것, 부분적으로 완화하는 것, 해결하지 못하는 것을 구분해서 말한다. 과장하지 않는 것이 에이전시 시장에서 신뢰를 쌓는 유일한 방법이라고 믿는다.

🚧 Who We Don't Serve — 우리가 섬기지 않는 고객
타겟 경계를 명확히 하는 이유

모든 사람을 위한 제품은 누구에게도 특별하지 않다. Scope Manager는 의도적으로 아래 고객을 타겟에서 제외한다. 이 선택이 핵심 고객에 대한 집중을 가능하게 한다.

❌ 5인 미만 초소형 에이전시 / 1인 사업자
계약·범위 관리의 체계 자체가 불필요한 규모. 클라이언트와 직접 구두로 해결 가능하고, 도구 도입 비용 대비 편익이 낮다.
구조 불필요 규모 관리 오버헤드 발생
❌ 20인 초과 중견 에이전시
자체 PM 팀, 법무 검토, 기존 계약 관리 시스템을 보유. 우리 제품이 해결하려는 문제를 이미 내부 프로세스로 해결하고 있다.
자체 해결책 보유 엔터프라이즈 영역
❌ 클라이언트 (발주자)
Scope Manager는 클라이언트를 설득하거나 압박하는 도구가 아니다. 철저히 에이전시 PM을 위한 내부 관리 도구다. 클라이언트 대면 기능은 만들지 않는다.
클라이언트 대면 ✕ 내부 도구 원칙
❌ 소프트웨어 개발사 / IT 컨설팅 대기업
변경 관리(Change Management) 프로세스가 이미 제도화된 조직. 전용 엔터프라이즈 CM 도구 또는 자체 시스템을 사용하며, 우리 제품의 가격·기능 범위와 맞지 않는다.

What We Build
우리가 실제로 만드는 것은 무엇인가 — 핵심 기능과 고객에게 제공하는 전환을 정의합니다.
The Core Promise
"클라이언트 요청이 들어온 순간부터
판정·근거·기록이 자동으로 완성된다"
PM이 해야 할 일은 단 하나 — 클라이언트에게 결과를 전달하는 것.
판단하고, 근거를 만들고, 기록하는 모든 과정은 Scope Manager가 처리한다.
⚙️ Core Features — 핵심 기능 3가지
⚖️
범위 초과 자동 판정
Feature 01 P0 — MVP 필수
고객 언어
"클라이언트가 '이것도 해주세요'라고 하면, 저는 계약 내용과 비교해서 범위 밖인지 아닌지를 시스템이 먼저 판정해줍니다. 제가 판단하는 게 아니에요."
해결하는 고통점
  • S-1 추가 요구 발생 시 비용 청구 포기 (심각도 92%)
  • I-3 범위 판단을 혼자 감수하는 구조
  • R-2 관계 중심 문화에서 계약 기준 제시 불가
작동 방식
  • 계약서 범위를 텍스트로 등록 → Claude API가 파싱·구조화
  • 클라이언트 요청 입력 → 계약 범위와 자동 비교·판정
  • 판정 결과: 범위 내 / 범위 초과 / 판단 필요 3단계
📄
청구 근거 리포트 자동 생성
Feature 02 P0 — AHA 모멘트
고객 언어
"판정 결과가 나오면 '시스템 상 계약 범위를 초과한 요청으로 분류되었습니다'라는 리포트가 자동으로 만들어져요. 이걸 그냥 클라이언트한테 보내면 되는 거예요."
해결하는 고통점
  • I-2 기록은 있지만 꺼내 쓸 수 없는 형태 (심각도 80%)
  • S-1 PM이 직접 말해야 하는 심리적 부담
  • I-1 "이번 한 번만"을 반복하며 선례 형성
작동 방식
  • 판정 완료 즉시 → 리포트 자동 초안 생성
  • PM이 검토 후 → 1클릭 이메일 발송 / PDF 다운로드
  • 리포트 언어: 객관적·중립적 시스템 어조
📈
프로젝트 손익 누적 기록
Feature 03 P1 — Pro 업셀
고객 언어
"이번 프로젝트에서 추가 요청이 총 몇 건 있었고, 그중 몇 건을 청구했고, 실제로 얼마가 손실됐는지 한눈에 보여요. 다음 견적 낼 때 이 데이터 기준으로 단가를 올릴 수 있어요."
해결하는 고통점
  • S-3 프로젝트가 끝나야 적자인지 아는 구조 (88%)
  • I-4 다음 견적 만회 시도 — 악순환 반복
  • R-1 업계 단가 표준 부재 — 간접 완화
작동 방식
  • 판정·청구 이력 자동 누적 → 프로젝트별 손익 시각화
  • 추가 요청 수 / 청구 성공률 / 실질 손실액 자동 계산
  • 누적 데이터 → 다음 견적 단가 기준 수치 제공

  • 근거가 있으니 클라이언트 콜이 덜 무섭다
  • 관계와 수익을 동시에 지킬 수 있다는 확신

  • 시스템 판정 결과로 대표 보고 간소화
  • 프로젝트 중간에 실시간 손익 확인
③ 결과의 전환 — Outcome Transformation
Before

  • 다음 견적에서 만회 시도 → 수주율 하락
  • PM 개인의 담력이 수익성을 결정

→
After

  • 시스템 판정이 수익성을 구조적으로 보호
  • 손실 클라이언트 패턴 인식 → 재계약 협상

What We Don't Build
하지 않기로 결정한 것들 — 명확한 경계가 제품의 정체성을 만듭니다.
🧭 "하지 않기로 결정한 것들"이 왜 중요한가

제품의 정체성은 무엇을 만드느냐만큼 무엇을 만들지 않느냐로 결정된다. 아래 목록은 요청이 들어와도 빌드하지 않기로 의식적으로 선택한 기능들이다. 각 결정에는 사용자 리서치와 비즈니스 판단에 기반한 명확한 근거가 있다.

🚫 빌드하지 않는 기능 — 이유와 함께
🙅
클라이언트 설득·협상 도구
절대 빌드 안 함
빌드하지 않는 것
  • 클라이언트에게 직접 발송되는 협상 제안서
  • 클라이언트 포털 / 클라이언트 로그인 기능
  • 클라이언트를 설득하는 논리 자동 생성
왜 안 하는가
한국 비즈니스 문화에서 클라이언트가 "도구가 나를 압박한다"고 느끼는 순간 관계가 파괴된다. 리서치 초기에 클라이언트 대면 기능을 탐색했다가 포기한 이유다. Scope Manager는 철저히 에이전시 내부 도구다.
📋
범용 PM / 프로젝트 관리 도구
절대 빌드 안 함
빌드하지 않는 것
  • 칸반 보드 / 스프린트 관리 / 타임라인
  • 팀원 업무 배분 / 리소스 관리
  • 일반 일정 관리 / 마일스톤 추적
왜 안 하는가
Jira·Notion·Asana와 경쟁할 이유가 없다. 우리가 해결하는 문제는 과업 관리가 아니라 범위 협상과 수익 방어다. 범용화는 포지셔닝을 희석시키고 개발 리소스를 분산시킨다.
📱
모바일 앱 / 반응형 우선 개발
MVP 이후로 연기
빌드하지 않는 것
  • iOS / Android 네이티브 앱
  • MVP 단계 태블릿·모바일 반응형 UI
  • 푸시 알림 / 모바일 전용 기능
왜 지금은 안 하는가
에이전시 PM의 핵심 사용 시나리오는 사무실 데스크톱 환경이다. 모바일 반응형은 v1.1로 연기. PMF 검증 전에 플랫폼을 확장하는 것은 리소스 낭비다.
🧾
자동 청구서 발송 / 결제 연동
MVP 이후 검토
빌드하지 않는 것
  • 클라이언트에게 청구서 자동 발송
  • 온라인 결제 / 인보이스 시스템
  • 세금계산서 / 회계 연동
왜 지금은 안 하는가
청구는 PM의 최종 판단과 관계 맥락이 필요한 영역이다. 자동화하면 오히려 관계 손상 리스크가 높아진다. 우리는 근거를 만들어줄 뿐, 발송은 PM이 결정한다.
📝
AI 자동 계약서 생성 / 법무 조언
범위 외
빌드하지 않는 것
  • 계약서 자동 초안 생성
  • 법적 분쟁 대응 조언 / 법무 기능
  • 계약 조항 검토·추천
왜 안 하는가
법무 영역은 전문 서비스 영역이다. AI가 생성한 계약서로 인한 책임 리스크는 제품 신뢰를 치명적으로 훼손할 수 있다. 우리는 기존 계약을 기준으로 판정할 뿐, 계약 자체를 만들지 않는다.

Design Principles
제품을 만드는 모든 결정의 기준 — 기능이 아니라 원칙이 제품의 성격을 결정합니다.
📐 디자인 원칙이란 무엇인가

디자인 원칙은 UI 가이드라인이 아니다. "이 기능을 만들어야 하는가", "이 문구는 어떤 어조여야 하는가", "이 화면에서 무엇을 먼저 보여줘야 하는가"를 결정할 때 기준이 되는 철학이다. 모든 팀원이 같은 판단을 내릴 수 있도록 원칙을 명문화한다.

🧘
01
Calm Authority
침착한 권위
원칙 설명
Scope Manager는 흥분하지 않는다. 판정 결과를 전달할 때도, 손실 데이터를 보여줄 때도 항상 조용하고 단호한 어조를 유지한다. 감정적 언어, 경고 아이콘 과다 사용, 불안을 자극하는 문구는 제품의 성격과 맞지 않는다.
실제 적용 예시
  • ✕ "⚠️ 위험! 범위를 초과했습니다!"
  • ✓ "이 요청은 계약 범위를 초과합니다."
  • 다크 네이비 컬러 팔레트 — 불안이 아닌 신뢰를 유발
  • Green·Orange·Yellow는 AI 판정 상태에만 사용 (장식 금지)
📊
02
Data Speaks First
데이터가 먼저 말한다
원칙 설명
모든 판정, 리포트, 손익 수치는 PM의 의견이 아닌 데이터의 결론으로 표현된다. "저는 이게 추가라고 생각합니다"가 아니라 "시스템이 계약 항목 3.2조와 비교한 결과입니다"의 언어를 쓴다. PM은 데이터를 전달하는 채널이 된다.
실제 적용 예시
  • 리포트 언어: "계약서 [항목]과 비교 시 범위 초과로 분류됩니다"
  • 손익 대시보드: 수치 먼저, 해석 나중
  • 판정 근거에는 계약서 원문 발췌 함께 표시
  • AI 판정 신뢰도 수치 표시 — 불확실한 경우 솔직하게 표기
🤝
03
Protect the Relationship
관계를 보호한다
원칙 설명
우리의 목표는 클라이언트를 이기는 것이 아니다. PM이 관계를 손상시키지 않고도 계약 기준을 지킬 수 있도록 돕는 것이다. 리포트 언어는 중립적이어야 하고, 어떤 기능도 클라이언트를 적으로 만들어서는 안 된다.
실제 적용 예시
  • ✕ "클라이언트의 무리한 요구"
  • ✓ "계약 범위를 초과하는 요청"
  • 리포트 수신자 언어: 클라이언트가 읽어도 기분 나쁘지 않은 중립 어조
  • PM이 최종 발송 여부 결정 — 자동 발송 없음
🌱
04
Earn Trust Progressively
신뢰는 점진적으로 쌓인다
원칙 설명
처음부터 모든 기능을 요구하지 않는다. 사용자가 작은 성공을 경험할수록 점점 더 많은 것을 맡긴다. Free → Starter → Pro는 기능의 계층이 아니라 신뢰의 계층이다. 온보딩은 최대한 단순해야 한다.
실제 적용 예시
  • 첫 화면: 계약 범위 등록 한 가지만 요구
  • 첫 AHA 모멘트까지 클릭 수 최소화
  • 기능은 필요할 때 점진적으로 공개 — Progressive Disclosure
  • Free 플랜에서도 핵심 가치 경험 가능하게 설계
✦
05
Less But Better
적게, 그러나 더 잘
원칙 설명
기능 수가 제품의 가치를 결정하지 않는다. 핵심 시나리오 1개를 완벽하게 수행하는 것이 50개의 평범한 기능보다 낫다. 모든 신규 기능 제안은 "이것이 없으면 핵심 사용자가 이탈하는가"라는 질문을 통과해야 한다.
실제 적용 예시
  • MVP 화면 수: 최소한으로 유지
  • 설정 옵션: 꼭 필요한 것만 — 결정 피로 제거
  • 신규 기능 추가 전 "MVP에서 필수인가" 체크
  • 디자인 시스템: 컴포넌트 재사용 극대화 — shadcn/ui 활용
